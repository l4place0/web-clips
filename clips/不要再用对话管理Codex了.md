# 总结稿

## 核心摘要

**视频内容：** 讲者认为，复杂的 Codex 工作不应继续以“对话列表”为主要管理界面，因为同一功能的讨论、实现与修复可能分散在多个会话中，海量聊天记录会淹没真正需要追踪的上下文。他演示的替代方案是一个自定义任务看板：工作以任务或功能为单位进入积压池、待办、进行中、审核中和完成等状态；Codex 定时领取任务，人通过评论追加要求并在审核节点决定是否推进。

任务卡不隶属于某一条对话，而是索引同一工作线上的多个 Codex 会话。这样，对话成为某次执行的临时界面，任务则成为较稳定的上下文载体：它保存需求说明、执行摘要、评论、修改记录和会话入口。尚未成熟的想法先留在积压池，只有进入待办后才会被自动领取，避免“一提出想法，Agent 就立即执行”。

## 从看板到可持续 Loop

**视频内容：** 看板还把人的工作时间与 Agent 的运行时间解耦。讲者可以先记录需求；当额度或自动化恢复时，Codex 再从待办池取任务。视频把同一机制扩展到自媒体选题：收藏的题目先进入积压池，筛选后由 Codex 调研，结果由人判断、评论并退回重做。

讲者指出，Loop 最容易失败在输入不足：如果每周仍需人专门给 Agent 布置选题，人的参与成本会让流程停止。他的做法是每周自动汇集自己点赞和收藏的文章、视频，并提出把同事的 AI 相关收藏汇总到飞书多维表格，再抽取为候选任务。这些属于讲者的私人实现与团队设想，本次无法独立验证为 Codex 的通用内置能力。

## 人工判断与 Graph 扩展

**视频内容：** 降低人的日常参与不等于取消人工判断。对于来自 GitHub issues 等不可信外部输入，讲者建议先进入积压/筛选阶段，并在执行前增加人工审核。线性看板适合按状态推进的任务；当一份脚本可能分支为文章、图片或视频等不同产物时，则需要可分支的 Workflow/Graph，把条件、Skill、MCP 或 API 动作组织为显式流程。

**外部核验补充：** OpenAI 将网页、文档、邮件和搜索结果等外部内容视为潜在的提示注入表面，并建议采用分层防护以及在高影响动作前让用户确认。人工审核能降低风险，但不能单独保证安全。[OpenAI：Understanding prompt injections](https://openai.com/safety/prompt-injections/) · [GPT-5.1-Codex-Max System Card](https://deploymentsafety.openai.com/gpt-5-1-codex-max)

**AI 辅助推断：** 视频真正主张的是把“对话管理”升级为“任务状态管理”：任务有明确入口、状态、证据、反馈和人工闸口，Agent 才能异步运行。看板本身不保证可靠；如果任务没有验收条件、权限边界、失败策略和可审计产物，它只会把聊天黑箱换成看板黑箱。

# 辅助理解

## 辅助理解：对话是执行窗口，任务才是工作单元

**视频内容：** 视频反对的不是使用对话，而是用对话列表承担项目管理。帧 2 把新工作入口改为任务看板；帧 4 进一步说明任务可以跨多条对话承载上下文。

![关键帧 2](assets/bilibili-BV1YWud6qEPj-frame-0002.webp)

![关键帧 4](assets/bilibili-BV1YWud6qEPj-frame-0004.webp)

```mermaid
flowchart LR
    I[想法或外部输入] --> B[积压事项]
    B -->|人工筛选 / 自动规则| T[待办事项]
    T -->|Agent 领取| W[进行中]
    W --> E[执行记录、产物与会话链接]
    E --> R[审核中]
    R -->|通过| D[完成]
    R -->|评论与退回| T
    R -->|风险过高| S[停止或人工升级]
```

这个模型把两类身份分开：

| 对象 | 主要职责 | 生命周期 |
|---|---|---|
| 对话 | 某次分析、实现或修复的交互记录 | 可被压缩、切换或新建 |
| 任务 | 目标、状态、反馈、产物与相关会话的索引 | 跨多次执行持续存在 |

**AI 辅助推断：** 任务卡可视为“单一工作事实源”，但前提是关键结论和产物真的回写任务；若真实决策仍散落在聊天中，看板只提供了视觉上的整齐。

## 1. 状态机让人和 Agent 异步协作

帧 5 展示“积压事项、待办事项、审查中、完成”等列。它的解释价值不只是任务很多，而是不同状态拥有不同权限：积压代表尚未授权执行，待办代表可领取，审核中代表 Agent 不应自行宣布业务完成。

![关键帧 5](assets/bilibili-BV1YWud6qEPj-frame-0005.webp)

**视频内容：** 这种任务池允许人在 Agent 忙碌、额度不足或自己离线时继续记录需求，自动化恢复后再领取任务。这里描述的是讲者自建流程，不应外推为所有 Codex 环境都会自动按额度调度。

## 2. Loop 的瓶颈常在输入供给，而非执行速度

帧 7 展示选题调研 Loop：兴趣选题进入积压池，经筛选后由 Codex 调研，最终回到人工判断。视频指出，如果“提供新选题”本身需要固定、额外的人工作业，这个循环很难持续。

![关键帧 7](assets/bilibili-BV1YWud6qEPj-frame-0007.webp)

```mermaid
flowchart TD
    A[日常自然产生的信号] --> B[静默汇集候选项]
    B --> C[去重、分类与风险标记]
    C --> D[积压池]
    D --> E{需要人判断吗？}
    E -->|是| F[人筛选优先级与范围]
    E -->|低风险且规则明确| G[自动进入待办]
    F --> G
    G --> H[Agent 执行]
    H --> I[证据与产物]
    I --> J[人工审核或确定性门禁]
    J -->|退回| G
    J -->|通过| K[完成]
```

**AI 辅助推断：** “降低人的成本”应优先减少机械搬运，而不是删除高价值判断。自动收集、归类、去重可以静默运行；需求授权、风险接受和结果验收是否可自动化，则取决于错误代价和规则是否足够明确。

## 3. 不可信输入必须经过边界检查

**视频内容：** 讲者以 GitHub issues 为例提醒，外部人员可能提交恶意内容，因此应保留人工审核，而不是让 Codex 无条件把输入直接变成执行任务。

**外部核验补充：** 这一风险方向与 OpenAI 对提示注入的说明一致：外部网页、文档和消息可能携带诱导 Agent 偏离用户意图的指令，高影响动作需要分层控制和确认。[OpenAI：Understanding prompt injections](https://openai.com/safety/prompt-injections/)

最低限度可以把入口分成三层：

- **收集层**：保留来源，不授予执行权限；
- **筛选层**：检查相关性、恶意指令、权限和预期影响；
- **执行层**：只接收明确授权、范围受限且有验收条件的任务。

这是基于视频风险提醒作出的 **AI 辅助工程化整理**，并非讲者逐项给出的产品规范。

## 4. 线性看板何时升级为 Graph

帧 10 展示“流程看板”配置界面，其中包含条件判断、Skill、MCP 和 API 等节点。它对应视频最后的判断：不是所有任务都能沿“待办→进行中→完成”单线前进，多种产物或条件路径需要显式分支。

![关键帧 10](assets/bilibili-BV1YWud6qEPj-frame-0010.webp)

```mermaid
flowchart LR
    T[已批准任务] --> P{产物类型}
    P -->|文章| A[写作流程]
    P -->|图片| I[图像工具 / API]
    P -->|视频| V[视频生成流程]
    A --> QA[独立检查]
    I --> QA
    V --> QA
    QA -->|证据不足| P
    QA -->|通过| H[人工发布判断]
```

**AI 辅助推断：** 升级为 Graph 的标准不应是“节点看起来更丰富”，而应是任务确实存在分支、并行、局部重试或不同权限。否则，简单看板更易理解，也更容易审计。
